# 摘要

随着我国人口老龄化进程加速，老年群体就医陪诊需求日益增长。传统陪诊服务存在信息不对称、流程不透明、医疗单据管理混乱等问题。本文设计并实现了一套面向老年群体的AI赋能陪诊助医服务系统，采用前后端分离架构，后端基于SpringBoot 3.2.x + MyBatis-Plus 3.5.x，前端基于Vue 3.4 + Element Plus，数据库使用MySQL 8.0。系统涵盖家属、陪诊师、管理员三类角色，实现了陪诊订单全闭环管理、医疗单据OCR识别建档、诊前就诊告知书生成、医嘱通俗化解读、就医档案隐私脱敏等核心功能。针对外部AI服务的不稳定性，设计了超时重试、熔断降级、异步任务、调用审计等九项工程化保障机制。针对医疗数据敏感特性，设计了基于角色上下文的动态脱敏方案与AES加密存储策略。经功能测试（53条用例）、集成测试（21步全流程）与性能测试方案验证，系统功能完整、状态机流转正确、脱敏策略有效。

**关键词**：陪诊服务；AI赋能；隐私脱敏；SpringBoot；Vue；OCR识别

# 第1章 绪论

## 1.1 研究背景与意义

### 1.1.1 人口老龄化与就医陪诊需求

根据国家统计局数据，截至2025年末，我国60岁及以上人口已突破3亿，占总人口比例超过21%。老年群体普遍面临出行不便、对医院数字化流程不熟悉、医疗信息理解困难等问题。在子女因工作等原因无法陪同时，专业陪诊服务成为刚需。

然而，当前陪诊行业存在以下痛点：（1）服务流程碎片化——从预约、派单、服务执行到费用结算缺乏统一的数字化管理平台；（2）信息透明度不足——家属无法实时了解陪诊进度与就医结果；（3）医疗单据管理混乱——纸质检验单、处方、病历难以系统归档与检索；（4）缺乏智能化辅助——陪诊师在就诊前准备、医嘱理解等方面缺乏工具支撑。

### 1.1.2 AI技术在医疗辅助场景的应用前景

随着OCR（光学字符识别）与大语言模型技术的成熟，AI在医疗辅助领域展现出显著应用价值。OCR技术可将纸质医疗单据数字化，实现检验指标的结构化提取与归档；大语言模型可基于患者档案生成个性化的就诊告知书，并以通俗语言解读专业医嘱。将AI能力嵌入陪诊服务流程，可显著提升服务效率与用户体验。

### 1.1.3 医疗数据隐私保护的迫切性

医疗数据涉及患者敏感个人信息，《个人信息保护法》《数据安全法》等法规对医疗数据的收集、存储、使用提出了严格要求。陪诊系统需在业务可用性与隐私保护之间取得平衡——陪诊师在服务窗口期需要老人的联系方式与基本健康信息，但服务结束后应自动收回访问权限。这要求系统设计阶段就嵌入细粒度的隐私保护机制。

# 第2章 相关技术介绍

## 2.1 SpringBoot框架

SpringBoot是基于Spring Framework的快速应用开发框架，通过自动配置（Auto-Configuration）与起步依赖（Starter）简化了Spring应用的构建与部署。本系统采用SpringBoot 3.2.5版本，该版本基于Jakarta EE 9+命名空间（`jakarta.*`替代`javax.*`），要求JDK 17及以上运行环境。

在后端架构中，SpringBoot承担以下职责：（1）内嵌Tomcat容器提供HTTP服务；（2）通过`spring-boot-starter-web`集成Spring MVC实现RESTful API；（3）通过`spring-boot-starter-aop`支持面向切面编程，实现`@RequireRole`注解的方法级角色控制；（4）通过`spring-boot-starter-validation`集成Bean Validation（Jakarta Validation），对DTO入参进行声明式校验。

## 2.2 MyBatis-Plus持久层框架

MyBatis-Plus是MyBatis的增强工具，在保留MyBatis原生SQL能力的基础上，提供了一系列开箱即用的CRUD方法（`selectById`、`insert`、`update`、`delete`）、条件构造器（`LambdaQueryWrapper`/`LambdaUpdateWrapper`，类型安全）、分页插件（`IPage`）与乐观锁支持（`@Version`注解）。

本系统选用MyBatis-Plus 3.5.5版本，使用`mybatis-plus-spring-boot3-starter`适配SpringBoot 3.x。关键应用场景包括：

- **订单并发控制**：通过`@Version`注解在`escort_order.version`字段上实现乐观锁，状态变更时执行条件UPDATE（`WHERE status=? AND version=?`），影响行数为0时抛出业务异常（409 Conflict）。
- **逻辑删除**：全表统一`deleted`字段配合`@TableLogic`注解，删除操作自动转为UPDATE。
- **条件构造器**：所有动态查询使用`LambdaQueryWrapper`，以Lambda表达式替代字符串字段名，避免字段重命名带来的维护风险。

## 2.4 MySQL数据库

MySQL 8.0是本系统的关系型数据库，所有业务表统一采用InnoDB存储引擎（支持事务、行级锁、外键约束）与utf8mb4字符集（支持完整的Unicode字符集，包括emoji）。本系统共设计13张业务表，包含40余个索引。

在数据库设计层面：

- **枚举字段**：所有枚举字段采用VARCHAR存储代码值，禁止使用MySQL ENUM类型。原因是ENUM增删枚举值需ALTER TABLE DDL操作，可维护性差，不符合持续交付最佳实践。
- **外键策略**：所有表统一使用逻辑外键（应用层维护引用完整性），不建物理外键约束。理由：避免级联操作的不确定性、提升批量写入性能、降低表结构变更的影响范围。
- **金额字段**：一律使用`DECIMAL(10,2)`类型，禁止FLOAT/DOUBLE。DECIMAL以字符串形式精确存储十进制数值，避免二进制浮点数无法精确表示十进制货币值（如0.1+0.2≠0.3）导致的舍入误差。
- **敏感字段**：身份证号使用AES加密后以VARCHAR存储密文，注释标注"密文存储，密钥走配置"。生产环境密钥应通过KMS或环境变量注入。
- **公共字段**：全表统一`id`（BIGINT UNSIGNED自增主键）、`create_time`/`update_time`（DATETIME自动填充）、`deleted`（TINYINT逻辑删除，对应MyBatis-Plus `@TableLogic`）。

## 2.5 OCR与大模型工程化对接概述

本系统的AI辅助功能（医疗单据OCR识别、就诊告知书生成、医嘱通俗化解读）依赖外部AI服务。鉴于外部服务的不确定性（网络抖动、服务限流、临时不可用），工程化对接需关注以下方面：

### 2.5.1 HTTP客户端

采用OkHttp 4.12.x，配置连接池（最大空闲连接5、保活时间5分钟）、统一拦截器注入鉴权头（`Authorization: Bearer {apiKey}`，具体格式以对应官方文档为准）。OCR与LLM使用独立客户端实例，分别配置15秒和30秒的读取超时。

### 2.5.2 超时与重试

连接超时3秒，读取超时15秒（OCR）/30秒（LLM）。仅对网络超时、HTTP 5xx、HTTP 429触发重试，指数退避（1s→2s→4s），最多3次。HTTP 4xx业务错误不重试，直接返回失败。每次重试记录`retry_count`到`ai_task`表。

### 2.5.3 熔断降级

本地实现基于`AtomicInteger`失败计数+最后失败时间戳的简易熔断器（不引入Hystrix/Sentinel等额外中间件）。连续失败5次进入降级状态，60秒后半开试探，试探成功恢复。降级期内：
- OCR接口：直接返回"识别暂不可用，请人工录入"，前端开放人工录入入口。
- LLM接口：返回预置模板文案，显著提示需人工补充。

### 2.5.4 异步化与幂等

OCR识别提交后立即返回`taskId`，由自定义线程池（核心线程4/最大8/队列50/CallerRunsPolicy拒绝策略）异步执行。选择`CallerRunsPolicy`的理由：队列满时由调用者线程同步执行，避免任务丢失；OCR调用本身由外部IO主导，不会长时间占用CPU。同一单据重复提交按（单据ID+任务类型）查重，RUNNING中返回原taskId，SUCCESS中直接返回结果。

### 2.5.5 结果校验与审计

- **OCR结果校验**：JSON结构校验 + 必填字段非空校验 + 字段格式正则校验（日期yyyy-MM-dd、金额数值、枚举值合法）+ 置信度阈值0.85以下标记`manual_confirmed=false`待人工确认。
- **LLM结果校验**：非空校验、长度上限校验、免责声明强制拼接。
- **调用审计**：每次调用记录`ai_task`表，`request_digest`/`response_digest`仅存储摘要文本与SHA-256哈希值，禁止明文存储请求/响应体全文。记录耗时、重试次数、最终状态。
- **免责声明**：所有大模型生成内容入库时强制拼接「AI生成内容仅供参考，不构成任何诊疗建议」，前端展示时以独立醒目样式呈现。

## 3.3 功能需求

### 3.3.1 核心业务功能模块

基于角色用例分析，系统功能划分为四大核心模块：

**（1）陪诊订单全闭环管理模块**

覆盖下单预约→派单/接单→状态流转→费用结算→服务评价的完整业务流程。关键需求包括：
- 下单前费用试算（BASIC型50元/h、EXAM型80元/h，不足1h按1h计）
- 订单幂等性保障（客户端requestId唯一索引防重复提交）
- 订单状态机8状态10流转规则严格校验
- 乐观锁并发控制（条件UPDATE + 影响行数为0即拒绝）
- 取消退款规则（PENDING_DISPATCH/DISPATCHED全额退，ACCEPTED退80%且距预约≥2h）
- 模拟支付（下单即PAID，退款为模拟账目流转）
- 评价唯一性（每单一评，数据库唯一索引兜底）

**（2）AI辅助服务模块**

- 医疗单据OCR识别：支持检验单/LAB_REPORT、处方/PRESCRIPTION、病历/MEDICAL_RECORD三类单据
- 诊前就诊告知书生成：基于订单信息+老人档案由LLM生成个性化告知书
- 医嘱通俗化解读：将专业医嘱文本转化为通俗语言
- OCR识别结果人工确认工作台：识别结果与原始图片左右对照，支持逐字段修正
- 所有AI生成内容强制标注「AI生成内容仅供参考，不构成任何诊疗建议」

**（3）就医档案与隐私脱敏模块**

- 就医档案CRUD（创建、修改、查询、删除），按角色可见性自动脱敏
- 医疗单据上传与管理（图片/PDF，限10MB，白名单后缀审核）
- 角色动态脱敏：家属全量可见、陪诊师窗口期电话全量、管理员脱敏视图
- 身份证号AES加密存储，日志敏感字段经DesensitizeUtil处理后输出
- 审核详情场景身份证号AES解密返回明文（仅ADMIN角色）

**（4）系统管理模块**

- 陪诊师资质审核（提交→审核→通过/驳回，含拒绝原因）
- 多角色账号鉴权（JWT + @RequireRole注解 + AOP）
- 运营统计看板（今日订单/待审核/累计用户/7日趋势）
- 用户状态管理（启用/禁用）
- 订单与评价管理（全量查询、筛选、结算、隐藏）

### 3.3.2 功能范围边界

以下功能不在本系统范围内：
- 在线问诊、电子处方开具
- 药品电商、药品配送
- 医保对接、真实支付网关
- 实时音视频通话
- 语音播报（标注为可选扩展项）

#### 外键策略说明

本系统统一采用逻辑外键（应用层通过Service代码维护引用完整性），不建物理外键约束（FOREIGN KEY）。理由如下：

1. **避免级联操作不确定性**：物理外键的ON DELETE CASCADE/ON UPDATE CASCADE在复杂业务流程中可能触发非预期的连锁删除/更新。
2. **提升批量写入性能**：物理外键在INSERT/UPDATE时需额外校验引用表中对应行是否存在，批量操作时成为性能瓶颈。
3. **降低表结构变更影响范围**：逻辑外键由应用代码控制，表结构变更（如字段类型调整）不需要同步调整外键约束。
4. **毕业设计实践**：本科毕设层面，逻辑外键足以保证数据一致性，物理外键的额外复杂度在本场景中收益有限。

### 4.2.2 核心表字段字典（简要）

全量表结构见`sql/01-schema.sql`与`src/main/resources/schema-h2.sql`。以下仅列出关键字段说明：

- **订单金额**：`escort_order.amount DECIMAL(10,2)`，单位元。不使用FLOAT/DOUBLE以避免二进制浮点无法精确表示十进制货币值（如0.1+0.2≠0.3）。
- **敏感字段**：`elderly_profile.id_card`、`escort_profile.id_card` 存储AES加密后的Base64密文，注释标注"密文存储，密钥走配置"。生产环境中密钥应通过KMS或环境变量注入。
- **枚举字段**：`escort_order.status`、`escort_order.service_type`、`escort_profile.audit_status`等全部使用VARCHAR存储代码值，禁止MySQL ENUM类型。ENUM增删枚举值需ALTER TABLE DDL操作，可维护性差。
- **乐观锁字段**：`escort_order.version INT DEFAULT 0`，MyBatis-Plus @Version注解自动管理，状态变更时条件UPDATE WHERE version=${oldVersion}，影响行数0即并发冲突。
- **逻辑删除**：全表`deleted TINYINT DEFAULT 0`，MyBatis-Plus @TableLogic自动将DELETE转换为UPDATE deleted=1。

### 4.3.4 并发控制设计

状态变更采用"条件UPDATE + 乐观锁"策略，禁止"先查后改"：

```sql
-- 乐观锁条件UPDATE（MyBatis-Plus LambdaUpdateWrapper生成）
UPDATE escort_order
SET status = #{targetStatus}, version = version + 1
WHERE id = #{orderId}
  AND status = #{expectedStatus}
  AND version = #{currentVersion}
```

影响行数为0时（状态已被其他操作修改），抛出`BizException(ResultCode.CONFLICT, "订单状态已变更")`。

禁止"先查后改"的裸操作（SELECT → 判断 → UPDATE），因为在SELECT和UPDATE之间的时间窗口内可能发生并发修改，导致状态覆盖（Lost Update问题）。乐观锁条件UPDATE在数据库层面保证原子性。

### 4.4.2 九项工程化机制详解

以下九项机制与`AiServiceImpl`、`AiHttpClient`、`SimpleCircuitBreaker`、`ThreadPoolConfig`的实际实现一一对应。

**机制1：HTTP客户端封装**

`AiHttpClient`为OkHttp单例，维护连接池（最大空闲连接5，保活时间5分钟）。OCR与LLM各自持有独立的`AiHttpClient`实例（`AiBreakerConfig`中声明两个`@Bean`），分别配置不同的`readTimeout`（OCR 15s、LLM 30s）。统一拦截器注入鉴权头`Authorization: Bearer {apiKey}`，具体格式以官方文档为准。

**机制2：超时控制**

连接超时3秒（`connectTimeout=3000`），读取超时按客户端类型区分。超时后统一抛出`AiTimeoutException`（继承自`AiApiException`，携带HTTP状态码），计入熔断器失败计数。Spring的`application.yml`中通过`ai.ocr.read-timeout-ms`和`ai.llm.read-timeout-ms`分别可配置。

**机制3：指数退避重试**

仅对以下三种异常触发重试：网络超时（`SocketTimeoutException`）、HTTP 5xx、HTTP 429（限流）。HTTP 4xx（如400参数错误、401鉴权失败）不重试，直接返回失败。重试策略：初始退避1秒，倍乘2（1s→2s→4s），最多3次。每次重试前`Thread.sleep(backoffMs)`，重试后`retry_count`递增写入`ai_task`表。第3次重试仍失败时，抛出`BizException(ResultCode.BAD_GATEWAY, ...)`。

**机制4：本地计数熔断降级**

`SimpleCircuitBreaker`基于`AtomicInteger`失败计数与`volatile long`最后失败时间戳实现。连续失败次数达到阈值（`circuit-failure-threshold=5`）时进入OPEN（降级）状态。降级期内所有请求直接返回降级响应，不实际发起HTTP调用。60秒后（`circuit-half-open-ms=60000`）进入HALF_OPEN状态，允许一次试探请求通过。试探成功→CLOSED（恢复正常）；试探失败→OPEN（重新计时60秒）。降级响应内容：
- OCR接口：返回`{"status":"DEGRADED","message":"识别暂不可用，请人工录入","result":null}`，前端开放人工录入入口。
- LLM接口：返回预置模板文案，前端显著提示"[系统提示] AI服务暂时不可用，以下为通用模板，请人工核实补充"。

该熔断器为本地内存实现，不依赖Redis等外部存储，不引入Hystrix/Sentinel/Resilience4j等第三方框架。

**机制5：异步任务执行**

OCR识别提交后，立即向`ai_task`表写入一条RUNNING记录并返回taskId给前端，实际OCR调用由自定义线程池异步执行。线程池配置（`ThreadPoolConfig`）：

| 参数 | 值 | 选择理由 |
|---|---|---|
| corePoolSize | 4 | 匹配OCR API的典型并发限制（多数API免费层为5 QPS） |
| maxPoolSize | 8 | 突发流量时弹性扩容，上限不超过数据库连接池 |
| queueCapacity | 50 | 缓冲峰值请求，避免瞬时拒绝 |
| RejectedExecutionHandler | CallerRunsPolicy | 队列满时由调用者线程同步执行，不丢任务，OCR调用IO密集型不长时间占用CPU |

禁止使用`@Async`默认线程池（`SimpleAsyncTaskExecutor`为每个任务创建新线程，无上限，存在OOM风险）。

**机制6：幂等性**

同一单据重复提交OCR识别时，按`(bizId, taskType)`组合查询`ai_task`表：
- 状态为RUNNING → 直接返回原taskId，不创建新任务。
- 状态为SUCCESS → 直接返回原识别结果，不重复调用API。
- 状态为FAILED/DEGRADED → 创建新任务重试。

此机制在`AiServiceImpl.submitOcr()`中实现，依赖数据库联合查询（`idx_biz_type`索引）。

**机制7：结果校验**

- **OCR结果校验**：在`AiServiceImpl.parseOcr()`私有方法中实现——JSON结构完整性校验（Jackson解析）+ 必填字段非空校验 + 置信度（confidence）< 0.85的记录标记为低置信度，前端OCR确认工作台高亮提示"待人工确认"。`parseOcr()`返回`OcrParsed`内部类，含`json`、`confidence`、`lowConf`三个字段。
- **LLM结果校验**：响应非空校验 + 长度上限校验（防止无限输出）+ 免责声明字段强制拼接。校验逻辑在`llmGen()`方法内联实现。

**机制8：调用审计**

每次AI调用在`ai_task`表持久化一条审计记录，包含：`task_type`（OCR/NOTICE/EXPLAIN）、`biz_id`（关联业务ID）、`status`（RUNNING/SUCCESS/FAILED/DEGRADED）、`retry_count`、`error_msg`、`start_time`/`end_time`/`cost_ms`、`request_digest`（请求摘要文本）、`response_digest`（响应摘要文本）。摘要字段仅存储SHA-256哈希值前缀（`AiServiceImpl.sha256()`私有方法，截取16位前缀），禁止明文存储敏感请求/响应体全文（防止医疗数据泄漏）。

**机制9：免责声明强制注入**

所有大语言模型生成的内容在落库时（`AiServiceImpl.llmGen()`私有方法），`disclaimer`字段固定赋值为：

> AI生成内容仅供参考，不构成任何诊疗建议

前端展示AI生成内容时，在内容区上方以独立醒目样式（`#FEF0E6`背景 + `#E6A23C`文字 + WarningFilled图标）重复展示该免责声明。该机制确保即使LLM输出中不含免责声明，系统层面强制注入。

### 4.5.1 脱敏策略表

### 4.5.2 双实现方案

**方案一：注解+序列化器（返回体级自动脱敏）**

`@SensitiveField(type = SensitiveType.XXX)` 注解标注于VO字段（如`MedicalRecordVO.elderlyName`、`MedicalRecordVO.diagnosis`），由`SensitiveFieldSerializer`（自定义Jackson `JsonSerializer`）在序列化时根据`UserContext.getUserRole()`动态决定脱敏策略。适用场景：Controller返回JSON给前端时自动脱敏，对业务代码透明。

**方案二：静态工具类（手工调用）**

`DesensitizeUtil`提供静态方法（如`DesensitizeUtil.name("张大爷")` → `"张**"`），用于日志输出、拼接消息、非标准VO场景等无法走Jackson序列化器的位置。适用场景：`log.info("用户: {}", DesensitizeUtil.phone(phone))`等。

### 4.5.3 角色-可见性矩阵

| 字段 | FAMILY | ESCORT（服务窗口期内） | ESCORT（非窗口期） | ADMIN |
|---|---|---|---|---|
| 姓名 | 全量 | 脱敏（NAME规则） | 脱敏（NAME规则） | 脱敏（NAME规则） |
| 联系电话 | 全量 | **全量**（业务必需：陪诊师需联系老人） | 脱敏（PHONE规则） | 脱敏（PHONE规则） |
| 身份证号 | AES密文存储，仅审核详情场景对ADMIN解密为明文 | 脱敏 | 脱敏 | 脱敏（审核详情例外） |
| 诊断结论 | 全量 | 脱敏（仅保留科室，DIAGNOSIS规则） | 脱敏 | 脱敏 |
| 详细住址 | 全量 | 脱敏（ADDRESS规则） | 脱敏 | 脱敏 |

**窗口期判断逻辑**：当前陪诊师`userId`是否存在与该档案关联的`escort_order`且状态为`ACCEPTED`或`IN_SERVICE`。存在→窗口期内；不存在→窗口期外。

**ADMIN审核详情idCard解密特例**：`GET /api/admin/escort/audit/{escortUserId}/detail`接口在`AdminServiceImpl.getAuditDetail()`中通过`aesUtil.decrypt(ep.getIdCard())`解密身份证号，返回明文至`EscortAuditDetailVO.idCard`字段。该VO为独立类，不与通用脱敏序列化器耦合，不可复用到其他场景。理由：资质审核业务上必须核对身份证号明文身份信息，无法通过脱敏后的星号掩码完成核验。

### 4.5.4 AES加密存储

身份证号在写入`elderly_profile.id_card`和`escort_profile.id_card`前，由Service层调用`AesUtil.encrypt(plainText)`加密为Base64密文。读取时由Service层调用`AesUtil.decrypt(cipherText)`解密。密钥通过`${encrypt.aes-key}`配置项注入，当前默认值为`escort-aes-key-2026-demo`（16字节）。**生产环境须使用KMS或环境变量注入密钥，毕设演示阶段使用本地配置**——此点在`application.yml`注释中明确标注。

### 4.5.5 日志脱敏

所有Controller层与Service层日志输出中，如涉及身份证号、手机号等敏感字段，统一经过`DesensitizeUtil`处理后输出。例如：

```java
log.info("用户登录成功: phone={}", DesensitizeUtil.phone(user.getPhone()));
// 输出: 用户登录成功: phone=138****1111
```

`GlobalExceptionHandler`在记录异常日志时同样执行脱敏处理，防止异常堆栈中携带敏感明文。

### 4.5.6 序列化流程图（文字版）

```
1. Controller 返回 Result<MedicalRecordVO>
   ↓
2. Jackson 序列化 MedicalRecordVO
   ↓
3. 遍历字段 → 发现 @SensitiveField(type = DIAGNOSIS)
   ↓
4. SensitiveFieldSerializer.serialize()
   ├─ 读取 UserContext.getUserRole() → ADMIN
   │  └─ 返回: "（已脱敏处理）"
   ├─ 读取 UserContext.getUserRole() → ESCORT
   │  ├─ 查询窗口期: 存在 ACCEPTED/IN_SERVICE 订单?
   │  │  ├─ 是: diagnosis → "（已脱敏处理）", phone → 全量
   │  │  └─ 否: diagnosis → "（已脱敏处理）", phone → "138****1111"
   │  └─ 返回对应脱敏结果
   └─ 读取 UserContext.getUserRole() → FAMILY
      └─ 全量返回原始值
   ↓
5. JSON 序列化完成 → 返回给前端
```
