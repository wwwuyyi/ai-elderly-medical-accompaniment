## 5.2 认证与鉴权实现

### 5.2.1 图形验证码

使用Hutool的`ShearCaptcha`（剪切扭曲验证码）生成4位字母数字混合验证码，宽160px高50px，干扰线3条。验证码答案存入HttpSession（key=`CAPTCHA_{captchaKey}`），有效期5分钟。前端以Base64图片Data URI直接渲染，无需额外的图片文件请求。

```java
// AuthServiceImpl.generateCaptcha() 核心逻辑
ShearCaptcha captcha = CaptchaUtil.createShearCaptcha(160, 50, 4, 3);
String code = captcha.getCode();
String captchaKey = UUID.randomUUID().toString().replace("-", "");
session.setAttribute("CAPTCHA_" + captchaKey, code.toUpperCase());
session.setMaxInactiveInterval(300); // 5分钟
// 返回 captchaKey + captchaImage(base64) 给前端
```

### 5.2.2 JWT签发与校验

使用jjwt 0.12.5（`jjwt-api`、`jjwt-impl`、`jjwt-jackson`三件套），HS256算法签名。登录成功后签发Token，有效期2小时（`application.yml`中`jwt.expiration=7200`可配置）。Token载荷包含`userId`、`username`、`role`三个声明。

```java
// JwtUtil.generateToken() 核心逻辑
String token = Jwts.builder()
    .subject(username)
    .claim("userId", userId)
    .claim("role", role)
    .issuedAt(new Date())
    .expiration(new Date(System.currentTimeMillis() + expiration * 1000L))
    .signWith(secretKey)
    .compact();
```

### 5.2.3 登录拦截器

`LoginInterceptor`对所有`/api/**`路径（排除`/api/auth/captcha`、`/api/auth/register`、`/api/auth/login`及Knife4j文档路径）进行Token校验。校验成功后从Token解析`userId`和`role`写入`UserContext`（ThreadLocal）。`afterCompletion`中调用`UserContext.clear()`清除ThreadLocal，防止Tomcat线程池复用导致的内存泄漏。

### 5.2.4 角色注解鉴权

`@RequireRole("FAMILY"/"ESCORT"/"ADMIN")`注解通过Spring AOP切面实现方法级角色控制。切面在方法执行前读取注解的`value`与`UserContext.getUserRole()`比对，不匹配时抛出`BizException(ResultCode.FORBIDDEN)`。

## 5.3 订单模块实现

### 5.3.1 订单号生成

订单号格式：`OD` + `yyyyMMdd` + 6位自增序列。`OrderNoGenerator`使用MyBatis-Plus Lambda查询当日最大序号，兼容MySQL与H2双数据库。插入纳入重试循环（最多3次），`DuplicateKeyException`按约束名分支处理（`uk_order_no`冲突重试、`uk_request_id`冲突幂等返回）。

### 5.3.2 下单流程

1. 校验老人档案存在且归属当前家属
2. 费用试算确认（`dto.getAmount()`与`estimate()`结果比对，不一致抛400）
3. `buildOrder()`构造实体（含requestId、金额、预约时间，status=PENDING_DISPATCH，pay_status=PAID——模拟支付）
4. 订单号生成+insert（3次重试循环）
5. `writeStatusLog()`写入首条状态日志
6. 通知管理员有新订单

### 5.3.3 乐观锁条件更新

所有状态变更统一使用`LambdaUpdateWrapper`的条件更新模式：

```java
int rows = orderMapper.update(null,
    new LambdaUpdateWrapper<EscortOrder>()
        .eq(EscortOrder::getId, orderId)
        .eq(EscortOrder::getStatus, currentStatus)   // 状态前置条件
        .eq(EscortOrder::getVersion, currentVersion) // 乐观锁版本号
        .set(EscortOrder::getStatus, targetStatus)
        .setSql("version = version + 1"));
if (rows == 0) throw new BizException(ResultCode.CONFLICT, "订单状态已变更");
```

### 5.3.4 取消退款规则

- T9取消（PENDING_DISPATCH/DISPATCHED）：`refund_amount = order.amount`（全额退款），`pay_status = REFUNDED`
- T10取消（ACCEPTED）：`refund_amount = order.amount × cancelRefundRate`（退80%，可配置），必填取消原因，距预约时间≥2小时
- IN_SERVICE后：不可取消

### 5.3.5 结算逻辑

管理员结算时，平台抽成按配置比例（`settlement.platform-rate=0.20`）计算：

```
platformFee = orderAmount × platformRate
escortIncome = orderAmount - platformFee
```

结算记录写入`settlement`表，`order_id`唯一索引保证一单仅一次结算。

## 5.4 AI模块实现

### 5.4.1 OCR异步识别

1. 前端POST `/api/ai/ocr/recognize`（传入单据ID）
2. 后端`AiServiceImpl.submitOcr()`：幂等查重 → 写ai_task（RUNNING）→ 提交线程池 → 立即返回taskId
3. 异步线程：OkHttp调用OCR API → 解析响应 → 结果校验（置信度阈值0.85）→ 更新ai_task状态
4. 前端每3秒轮询 `GET /api/ai/ocr/task/{taskId}`，直到状态为SUCCESS/FAILED/DEGRADED
5. SUCCESS后进入OCR确认工作台：识别结果与原始图片左右对照，支持逐字段修正
6. 人工确认后POST `/api/ai/ocr/task/{taskId}/confirm`，结果正式入库

### 5.4.2 熔断器实现

`SimpleCircuitBreaker`核心数据结构：

```java
private final AtomicInteger failureCount = new AtomicInteger(0);
private volatile long lastFailureTime = 0;
private volatile boolean open = false;
```

状态转换逻辑：
- `failureCount >= threshold(5)` → OPEN，记录`openTime`
- OPEN状态下经过`halfOpenMs(60000)` → HALF_OPEN，允许一次试探
- 试探成功 → CLOSED（`failureCount`重置为0）
- 试探失败 → OPEN（重新计时）

## 5.5 脱敏模块实现

### 5.5.1 注解驱动序列化器

```java
// Service层：MedicalRecordServiceImpl.checkVisibility() —
// 窗口期判断与标记设置（查询是否存在ACCEPTED/IN_SERVICE的关联订单）
Long windowCount = orderMapper.selectCount(new LambdaQueryWrapper<EscortOrder>()
    .eq(EscortOrder::getEscortId, userId)
    .eq(EscortOrder::getElderlyId, r.getElderlyId())
    .in(EscortOrder::getStatus, "ACCEPTED", "IN_SERVICE"));
UserContext.setPhoneFullAccess(windowCount > 0);

// 序列化器层：SensitiveFieldSerializer.serialize() — 读取标记决定脱敏
if ("ESCORT".equals(role)) {
    if (type == SensitiveType.PHONE && UserContext.isPhoneFullAccess()) {
        gen.writeString(value); // 窗口期内电话全量
        return;
    }
    gen.writeString(DesensitizeUtil.desensitize(value, type));
    return;
}
```

窗口期标记通过`UserContext.PHONE_FULL_ACCESS`（ThreadLocal Boolean）跨Service→序列化器传递，在`LoginInterceptor.afterCompletion`中随`UserContext.clear()`统一清除，防止线程池复用泄漏。

### 5.5.2 AES加密存储

用户注册陪诊师或创建老人档案时，身份证号在Service层经`AesUtil.encrypt()`加密后写入数据库。管理员审核详情接口调用`AesUtil.decrypt()`解密返回明文，仅在`EscortAuditDetailVO`中使用，不落缓存、不与其他VO复用。

## 5.6 前端关键实现

### 5.6.1 Axios封装

```javascript
// api/request.js
const api = axios.create({ baseURL: '/api', timeout: 15000 })

// 请求拦截器：注入JWT
api.interceptors.request.use(c => {
  const t = localStorage.getItem('token')
  if (t) c.headers.Authorization = 'Bearer ' + t
  return c
})

// 响应拦截器：统一错误处理
api.interceptors.response.use(
  r => {
    if (r.data.code !== 200) {
      ElMessage.error(r.data.message || '失败')
      return Promise.reject(r.data)
    }
    return r.data
  },
  e => {
    if (e.response?.status === 401) {
      localStorage.clear()
      router.push('/login')
    }
    ElMessage.error('网络错误')
    return Promise.reject(e)
  }
)
```

### 5.6.2 角色路由守卫

```javascript
// router/index.js beforeEach
router.beforeEach((to, from, next) => {
  const t = localStorage.getItem('token')
  const u = JSON.parse(localStorage.getItem('user') || 'null')
  if (to.meta.public) { next(); return }
  if (!t) { next('/login'); return }
  if (to.meta.role && u?.role !== to.meta.role) {
    // 角色不匹配，重定向到该角色的首页
    if (u?.role === 'FAMILY') next('/family/home')
    else if (u?.role === 'ESCORT') next('/escort/home')
    else if (u?.role === 'ADMIN') next('/admin/dashboard')
    return
  }
  next()
})
```

# 第7章 总结与展望

## 7.1 工作总结

本文设计并实现了一套面向老年群体的AI赋能陪诊助医服务系统，完成以下主要工作：

1. **需求分析与系统设计**：基于家属、陪诊师、管理员三类角色的用例分析，完成了系统功能需求与非功能需求建模。设计了13张数据库表（含16个E-R关系、16个关键索引）、8状态订单状态机（10条流转规则）以及角色-隐私脱敏策略矩阵。

2. **后端服务开发**：基于SpringBoot 3.2.5 + MyBatis-Plus 3.5.5实现62个REST API端点，覆盖认证鉴权、老人档案、陪诊师资质审核、订单全闭环管理（乐观锁+幂等+退款规则）、就医档案管理、AI服务调用、管理端运营监管等全部功能模块。

3. **AI模块工程化**：封装OkHttp HTTP客户端，设计并实现了超时控制、指数退避重试（3次）、本地计数熔断降级（连续5次失败进入降级、60秒半开试探）、异步任务（自定义线程池4/8/50+CallerRunsPolicy）、结果校验（置信度0.85阈值）、幂等查重、SHA-256审计摘要与免责声明强制注入共九项工程化保障机制。

4. **隐私脱敏设计**：实现了基于@SensitiveField注解+Jackson自定义序列化器的角色动态脱敏方案（家属全量、陪诊师窗口期电话全量+其余脱敏、管理员脱敏+审核详情idCard解密特例），配合AES加密存储与日志脱敏，全面覆盖数据的存储、传输与展示环节。

5. **前端三端开发**：基于Vue 3.4 + Element Plus开发27个页面组件（家属端适老化设计、陪诊师端OCR工作台、管理端脱敏预览），Vite构建通过（1721模块，约5秒）。

6. **测试设计**：编写53条功能测试用例、21步全流程集成测试（BUILD SUCCESS）、JMeter 5场景性能测试方案及18条安全测试用例（覆盖水平/垂直越权、未授权访问、SQL注入、XSS、脱敏有效性）。

## 7.2 不足与展望

本系统在以下方面存在不足，可作为后续改进方向：

1. **AI服务质量依赖外部API**：OCR识别与LLM生成的准确率、响应时间完全依赖所对接的外部AI服务。本系统虽设计了重试、熔断、降级等容错机制，但无法从根本上解决外部服务不可用或响应质量低的问题。后续可考虑引入本地小模型（如Tesseract OCR、轻量级LLM）作为降级方案。

2. **缺乏真实医疗数据验证**：全部业务数据为自行构造的模拟数据（医院名称虚构、患者档案虚构），OCR识别准确率、LLM生成质量未在真实临床场景下验证。若投入实际使用，需引入真实脱敏医疗数据进行效果评估。

3. **并发场景未充分验证**：虽然设计了乐观锁并发控制机制，但性能测试目前仅停留在方案设计阶段，未在MySQL生产环境下实际执行JMeter压力测试。真实并发场景下数据库连接池、线程池的参数调优需进一步实验。

4. **安全审计不完整**：当前仅对AI调用链路做了审计（ai_task表），未对管理员敏感操作（审核通过/驳回、用户禁用、评价隐藏）进行独立的操作审计日志。后续可扩展统一的审计切面。

5. **移动端适配有限**：前端虽针对家属端做了适老化设计（字号/按钮/对比度），但未做响应式布局适配。陪诊师在移动场景下通过手机浏览器访问Web页面体验不如原生App或微信小程序。后续可考虑开发微信小程序端。

6. **H2仅用于自测**：当前开发环境使用H2内存数据库，与生产MySQL在SQL方言、函数支持上存在差异（如日期函数、CAST语法），一定程度上增加了开发-生产环境不一致的风险。
